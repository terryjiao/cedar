# Cedar 产品路线图

Cedar 的目标是减少 Agent 行为实验的准备工作，让实验结果能够影响下一次开发。任务覆盖图是接入入口；后续核心能力是把任务变成可执行、可比较、可复用的实验，并把证据反馈给开发者。

当前已发布 v0.1.0：Skill、资料采集、证据校验和报告。实际运行目标 Agent、offline A/B 和自动改进尚未实现。当前状态见 [开发进度](progress.md)，立即要做的工作见 [下一里程碑](next-milestone.md)。

## 近期开发顺序

1. 验证 DSH 自动化入口是否保留目标产品实际使用的 prompts、工具、插件和输入上下文。
2. 在独立、可重建的状态中执行一个真实任务，保存输出和执行证据，并按明确标准判断结果。
3. 对同一任务运行 baseline 和 candidate，比较行为、结果与失败原因。

先支持 DSH，沿用用户现有 coding agent 与模型配置。客户业务规则通过输入和配置表达，保持 Cedar 核心通用。已有评测方法和开源工具可以作为实现基础，不以重建完整评测框架为目标。

## 六个月阶段规划

月份表示研发顺序和大致投入窗口，不是固定交付承诺。每阶段达到验证条件后，再扩大范围。

| 阶段 | 计划能力 | 进入下一阶段前需要的证据 |
| --- | --- | --- |
| 第 1 月 | 完成接入，并打通 DSH 单任务执行与最小 A/B 探针 | 测到真实产品行为；能说明人工准备成本和运行限制 |
| 第 2 月 | 可复用任务包，辅助准备输入、初始状态和判定标准 | 增加任务所需的人工工作下降；关键标准仍可审阅 |
| 第 3 月 | 根据变更选择实验，跨多次开发复用任务和结果 | 多次真实变更使用已有任务，结果实际影响开发决策 |
| 第 4 月 | 将失败证据交给 coding agent，在监督下提出改进并重新验证 | 改进能通过独立保留的检查，判定标准不会随候选修改而降低 |
| 第 5 月 | 接入第二个 DSH 项目，检验通用性 | 复用同一套核心能力，无需为每个项目重新编写一套流程 |
| 第 6 月 | 稳定的重复实验与开发反馈流程 | 团队持续使用，维护和接入所需的人工介入下降 |

## 如何验证产品价值

重点观察首次得到有用结果的时间、任务准备与纠错的人力、后续变更的复用程度，以及结果是否改变开发决策。比较对象包括使用相同资料的通用 coding agent 和已有评测工具。报告更美观或任务更多，本身不足以证明差异化。

## 长期方向

逐步支持围绕 prompts、工具、上下文组织和工作流的受监督改进循环。业务目标和关键约束由人设定；每次改进由独立实验重新检验。其他运行时的适配由实际需求驱动。

更长期的交付模式与商业探索不构成近期功能承诺。当前优先验证可复用产品能力，避免把每次接入都变成手工制作数据集或客户专属开发。
